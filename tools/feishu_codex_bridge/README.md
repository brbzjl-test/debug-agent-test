# 飞书 ↔ 本机 Codex 验证程序

通过已配置的飞书应用机器人，与本机 Codex 连续文字对话。Python 标准库实现，无需 pip 依赖、API Key 复制或公网回调服务。

```text
飞书私聊 → lark-cli 长连接 → Python / SQLite → codex exec
   ↑                                           ↓
   └──────── 机器人回复 ← 本地待发送队列 ←─────────┘
```

Codex 使用本机已有登录、模型和模型服务配置，工作目录默认指向本仓库。先在飞书选择【问题上报】【基于旧问题上报】或【普通聊天】；选定上报后，先生成 ID / sub-ID，再开始聊天。同一编号的连续消息通过 `codex exec resume <thread_id>` 延续上下文，各编号有独立会话。普通聊天单独保存，不自动写入问题台账。它运行独立的 Codex 会话，不会把飞书消息插入当前桌面聊天。

## 快速运行

要求 macOS / Linux、Python 3.9+、已登录的 `lark-cli` 和 Codex CLI。本次在 Codex CLI 0.153.4 上验证；程序使用该版本的非交互执行和功能开关。

在仓库根目录执行：

```bash
# 仅首次运行；复用当前飞书 profile，自动读取已配置用户的 open_id
python3 tools/feishu_codex_bridge/bridge.py init

# 检查机器人认证、Codex 登录和工作目录
python3 tools/feishu_codex_bridge/bridge.py doctor

# 可选：真实调用模型两轮，验证上下文延续（会消耗模型额度）
python3 tools/feishu_codex_bridge/bridge.py smoke-test

# 手动后台启动；终端关闭后继续运行，不设置开机自启动
python3 tools/feishu_codex_bridge/bridge.py start
python3 tools/feishu_codex_bridge/bridge.py status
python3 tools/feishu_codex_bridge/bridge.py stop

# 或前台运行，用 Ctrl+C 停止
python3 tools/feishu_codex_bridge/bridge.py run
```

本程序只手动启动，不注册开机或登录自启动。电脑重启后，需要再次执行 `start` 或 `run`。

`init` 不覆盖已有配置。如果 CLI 没有记录用户 open_id，使用 `init --allow-user ou_xxx`。生成的 `config.local.json` 已被 Git 忽略，里面只有路径、profile、允许的用户等设置，没有密钥。

配置也可以从 `config.example.json` 复制并填写，使用 `python3 tools/feishu_codex_bridge/bridge.py --config /path/to/config.json start`。配置中的相对路径以配置文件所在目录为基准。

启动后，私聊机器人发送 `/new`，进入“是否要上报问题”的选择卡片：

1. **问题上报**：立即建立新编号，例如 `ISS-20260911-XXXXXXXX`，状态 `open`。随后发送现象、设备、时间和日志。
2. **基于旧问题上报**：先从下拉列表选择旧 ID，再生成 `ISS-20260911-XXXXXXXX-S001`；再次上报依次为 `-S002` 等。创建后才开始收集本次信息。
3. **普通聊天**：显式选择不建单，再与 Codex 交流。

首次直接发送文字时，程序先返回选择卡片，不启动分析；选择后请重新发送现象。`/new` 会结束当前输入归属并返回入口，选择期间收到的文字不会误记到旧问题；已排队的消息保留原归属。

“继续本次问题”或 `/use ID` 沿用同一记录，适合补充日志和追问。“基于此问题再次上报”或 `/sub ID` 创建新一轮记录。sub-ID 的现象、聊天、Codex 会话、解决方案和验证状态独立；关闭某个 sub-ID 不改变父问题或其他 sub-ID。已解决的问题也可再次上报。选择一个 sub-ID 作为父问题时，新编号继续附加 `-S001`，保留完整关联路径。

创建 sub-ID 时保存父问题的标题、现象、当时状态和方案摘要为【旧问题参考】，首轮分析带入该快照；它不等同于本次证据，AI 不能直接假定根因相同。父问题后续修改不会悄悄改变这份参考。

也可以显式发送 `/report 现象描述`，一步完成新建编号和首条现象提交。普通聊天不会因为出现“报错”等词被自动转为问题。每次新现象需明确选择上报，得到新 ID 或 sub-ID。

| 飞书命令 / 操作 | 行为 |
| --- | --- |
| 【问题上报】或 `/report 现象` | 建立独立问题，初始状态 `open` |
| 【基于旧问题上报】或 `/sub` | 选择旧 ID，先创建 sub-ID，再聊天收集信息 |
| `/sub 问题编号` | 基于指定旧 ID 创建 sub-ID，初始状态 `open` |
| `/issues` | 查看自己最近 30 个问题，开发人员可看其支持范围内的问题 |
| `/use 问题编号` | 切换到旧问题继续追问；已经排队的消息仍属于发送时的原问题 |
| `/issue 问题编号` | 查看该问题状态、现象、方案、最近 12 条记录和独立记录入口 |
| `/history 问题编号` | 打开该问题独立的完整聊天与处理记录 |
| `/chat` | 显式选择普通聊天；问题仍保留 |
| `/verify 问题编号 解决方案 \| 验证步骤` | 已配置的开发人员提交【待验证】 |
| 【已解决】或 `/confirm 问题编号` | 只有本次上报的现场人员可以确认，且必须已经【待验证】 |
| 【仍有问题】或 `/reopen 问题编号` | 现场验证未通过，退回 `open` 继续排查 |
| `/status` | 查看当前问题、连接和队列状态 |
| `/help` | 显示使用说明和操作卡片 |
| `/new` | 返回入口，等待重新选择；不创建编号 |

状态固定为：`open → 待验证 → 已解决`；验证未通过时 `待验证 → open`。

AI 通过结构化输出区分“仍在排查”和“已给出解决方案”。只有明确给出解决方案和验证步骤，程序才申请进入【待验证】；普通回答、追问、猜测不会自动推进状态。AI 不能标记【已解决】。确认按钮绑定问题和方案版本，过期按钮不能确认新的方案。现场已经确认解决后，后来的 AI 回答也不能把它重新变为待验证。

选定入口后，每条待分析文字先收到保存提示，再收到 Codex 回答。问题内所有回复均显示问题编号，长回答分条发送。代码只读分析、现场操作由人完成。

## 飞书配置

使用**应用机器人**，普通群自定义 Webhook 机器人不能提供这里需要的收消息长连接。

- 应用启用机器人能力，并对使用者可见。
- Bot 可接收消息事件 `im.message.receive_v1`，具备单聊接收权限 `im:message.p2p_msg:readonly`。群内使用还需 `im:message.group_at_msg:readonly`；若要直接接收未 @ 机器人的 `/codex` 消息，还需开通 `im:message.group_msg` 并发布新版本。
- Bot 具备 `im:message:send_as_bot` 发消息权限。
- 在“事件与回调 → 回调配置”启用 `card.action.trigger`，并开通 `im:message:readonly`，让卡片按钮回调可被接收。CLI 显示 ready 只能证明消费者已启动，实际按钮回调需点击验证。
- 消息事件通过 `lark-cli event consume` 的长连接接入。启动日志出现 `[event] ready event_key=im.message.receive_v1` 表示消费者就绪；`feishu-websocket: connected` 表示已建立飞书连接。

程序默认只响应 `allowed_users` 中用户的私聊，防止其他使用者触发本机代码读取，也避免回复自己的消息形成循环。可选择将群 ID 加入 `allowed_group_chats`。开通全部群消息权限后可使用 `/codex /report`；只开通 @ 消息权限时，直接使用 `@小臂生产助手 /report` 或 `@小臂生产助手 当前日志`。机器人名称配置在 `bot_names`。这仍要求发送者在用户白名单中，并为机器人开通相应群消息接收权限。

话题群中，每个话题根消息是一个独立上下文：在新话题发送 `/codex /report` 会建立该话题的 ID；后续在同一话题发送 `/codex 日志补充` 只归入该话题。另开话题不会继承前一个话题的活动问题或 Codex 会话。卡片操作同样保留所在话题。若飞书事件没有提供根消息 ID，程序把首条消息 ID 作为该话题键，并保留原始事件供排查。

不需要飞书用户 OAuth 登录：收消息和回复都使用机器人身份。程序固定使用配置中的 profile，不跟随 CLI 当前账号切换。

## 多维表格问题管理

“现场问题追踪”包含两张关联表，并在【问题详情】目录中为每个问题建立一篇独立飞书文档：

- **问题台账**：一条上报对应一行，包括每个 sub-ID；包含编号、父问题编号、上报类型、现象、状态、上报人、时间、负责人、优先级、解决方案、验证步骤、现场确认人/时间、根因、hotfix 分支/提交等。可按【父问题编号】筛选关联上报。
- **处理记录**：每条现场消息、AI 回答、状态变更和验证结果独立记录，通过【所属问题】关联台账；长文本分段保存，保留全文。
- **独立问题文档**：标题使用问题编号，按时间顺序追加完整现场消息、Codex 回复和状态变化。问题台账的【完整记录】字段链接到对应文档；不同问题不会混在一起。

发送 `/history ID` 或在问题卡片中点击【打开完整记录】可直接查看。文档创建成功后，机器人也会在原话题发送一次链接。断网期间内容先保存在本地，联网后继续同步；同步标识用于避免重试时重复追加。台账仍可用于筛选、分派和管理状态。本地也可执行：

```bash
python3 tools/feishu_codex_bridge/bridge.py issues
python3 tools/feishu_codex_bridge/bridge.py issue ISS-20260911-XXXXXXXX
python3 tools/feishu_codex_bridge/bridge.py base-check
```

本地 `config.local.json` 的 `base` 配置：

```json
{
  "base_token": "实际创建结果返回的 token",
  "issues_table_id": "问题台账的实际 table_id",
  "history_table_id": "处理记录的实际 table_id",
  "url": "实际表格链接"
}
```

`engineer_users` 填写支持工程师的飞书 open_id；他们可在机器人中用 `/use` 查看和继续问题，用 `/verify` 提交解决方案，仍不能代替上报人确认已解决。该名单为空时，开发人员可在多维表格中填写【解决方案】【验证步骤】后将状态设为【待验证】，程序通常在 30 秒内读取并通知现场验证。

程序维护编号、现象、AI 分析、状态和现场确认字段；负责人、优先级、设备环境、根因复盘、hotfix 字段由工程师维护，同步不会覆盖。最终确认必须经机器人完成；直接在表中改【已解决】不能替代现场确认，程序下一次同步会恢复有依据的状态。多维表格所有者仍拥有直接编辑权限，本验证版没有设置字段级权限锁。

同步先检查真实字段名和类型，创建前按业务编号查询，写入成功后保存 record_id，失败时保留本地待同步记录。单实例串行写入；飞书不提供这里使用的业务编号原子唯一约束，不应让多个桥接实例同时写同一问题。此前普通测试聊天不会追溯建单或上传。

多维表格需要应用身份的表/字段/记录读写权限。创建资源还需要 `base:app:create`、表创建/更新/删除权限；机器人向当前用户授予新表访问权需要 `docs:permission.member:create`。这些权限与 IM 收发消息权限独立。

## 能力和记录

- Codex 只读分析配置目录内的代码、已有日志和用户发送的文字，不自动修改软件、安装依赖或操作机器人。
- 每次启动检查已配置的 MCP 服务并在子进程中关闭，同时关闭插件、Apps、Hooks、浏览器、电脑操作、多 Agent 和记忆功能。保留原模型配置；分析强度由 `reasoning_effort` 控制，默认 `medium`。
- Codex 使用 `read-only` 沙箱和 `never` 审批策略，忽略已有 shell 放行规则。涉及修改的解决步骤由人执行。只读文件访问不是严格的仓库目录隔离，故仅为白名单使用者开放。
- 入站消息按 `message_id` 去重，原始事件、时间和回答保存在本机 SQLite。模型分析和飞书发送分开；发送失败不会重新调用已完成的模型分析。
- 单个分析队列保持问题和追问的顺序；每条消息入站时即绑定问题 ID，切换问题不会改变已排队消息的归属。第一版为串行处理，一个慢问题会让后续普通问题等待，`/help` 和 `/status` 仍可直接回复。
- 发送失败时使用同一个幂等键重试。飞书服务端幂等窗口有限，超过窗口后遇到“发送已成功但响应丢失”的情况，不能保证绝无重复回复。
- Codex 调用失败最多尝试三次，之后发送失败提示，原问题仍保留。程序若在分析中退出，重启会提示重新发送，不会盲目重放可能已经执行过的模型轮次。
- 本地进程用文件锁防止同一状态目录重复启动。不要同时运行多个不同状态目录的桥接程序监听同一机器人和用户，否则它们会各自回复。

`status` 显示实际状态目录。自动生成配置默认放在 `~/.local/state/feishu-codex-bridge/<仓库标识>/`：

| 文件 | 用途 |
| --- | --- |
| `bridge.sqlite3` | 收到的消息、独立问题、处理记录、会话映射、回答、待发送/同步队列和失败记录 |
| `bridge.log` | 连接、收件、分析、回复状态；自动轮转 |
| `turns/<本次调用>/events.jsonl` | Codex 事件与工具执行记录 |
| `turns/<本次调用>/request.json` | 对应飞书消息 ID、开始时间与前序会话，方便追踪 |
| `turns/<本次调用>/answer.txt` | Codex 最终回答 |
| `turns/<本次调用>/stderr.log` | 单次 Codex 调用的诊断输出 |
| `launcher.log` | 后台启动输出 |
| `health.json` | 最近的本地进程与消费者状态 |

状态目录仅当前系统用户可读写。消息、代码片段和工具输出会形成诊断资料；本验证版不自动清理 SQLite 和 turns，需按实际留存要求管理磁盘空间。

**联网范围：**已经接收到本机的消息和待发送回复可在重启后继续处理；网络断开时尝试重连。电脑关闭、休眠或断网期间发到飞书的新消息，本版没有历史补拉，不能保证补收，请恢复连接后重发。`status` 的连接字段来自 CLI 最近一次状态通知，不是主动端到端探测。

本版不包含语音/电话录音、附件解析和现场环境自动快照。问题根因的跨事件归并、完整人工接管工作台仍待后续扩展。

## 验证与排查

```bash
python3 -m unittest discover -s tools/feishu_codex_bridge -p 'test_*.py' -v
```

没有回复时，先查看 `status` 和 `bridge.log`：没有“消息已保存”通常是机器人选择、用户白名单、事件或权限问题；已经保存但没有回答时查看对应 `turns` 调用记录；“发送失败”表示飞书回复权限、原消息可用性或网络存在问题。`doctor` 只验证本地认证状态；真实收发需向机器人发送消息确认。
